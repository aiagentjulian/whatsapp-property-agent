# WhatsApp Property Agent：Sales Brain V3 升级与 A/B 评估

**日期：**2026-10-13（MYT）

**分支：**`codex/sales-brain-v3-complete`，从 `codex/sales-core-v3` 的 `6f8d5a6` 建立。

**付费评估版本：**`f264663`。

**评估后修正：**`5f5fb9c`（相同待处理请求的复用与具体回复）、`eee9f04`（模拟正式交接时抑制 AI 草稿回复）；其后的 V2 上限恢复与 RESUMED 测试见本报告提交。

**生产状态：**默认仍为 V2；V3 未部署、未合并。

**建议：**保留 V2。V3 的结构更完整，但本轮盲评没有显示销售质量提升。

## 代码审计与根因

1. 旧 V3 Strategy 的 `max_output_tokens=900` 与 High 推理及结构化 JSON 同用，容易将推理预算挤入输出上限。旧 V3 Conversation 只看最近 8 条消息，而 Strategy 看 28 条；V2 则看最近 28 条。旧 V3 还过滤了 `next_objective` 等持久进度字段。
2. 旧 V3 没有传入 V2 常用的工作简报和已核实标准户型。知识检索只根据即时查询及策略文本选择 3 段，可能遗漏最基本的三房产品事实。
3. SQLite 只保存普通 Lead Profile 与完整消息，没有独立的销售反馈状态。Support Request 虽按精确签名复用，但措辞扩展后可生成语义重复的待处理请求；模型仍可能每轮重新承诺查询。
4. 旧模拟器要求尽量达到 6–10 轮，并在 Support Request 后立即重试同一客户消息，使“客户已经接受等待”变成人工追问。旧 Judge 看隐藏买家动机，并可能把很早结束的难客视作好的处理。初次新 Judge 的事实包过窄，误报了已记载的设施；扩展事实包后又因不知道授权的客户名称而误报“Pearl Residences”。这两个首案判定保留为审计文件，最终判定使用完整事实库与名称规则。
5. 旧运行说明曾提到 3 次 incomplete 响应及一次中断的部分 V3 对话未保存用量；没有可核查的原始 `incomplete_details`。因此不能从旧运行精确归因或重建费用。本次改为逐次持久化 usage、状态和延迟，不把 incomplete 当作成功。

## 实现

V3 仍用 GPT-6 Luna / High 两次请求：Strategy 根据完整近期对话、前次进度和运营状态更新理解与目标；Conversation 独立判断，再用已核实知识及工作简报作答。策略只是内部建议，不能覆盖客户说法、知识或系统能力。Strategy 上限 3,000；V3 Conversation 6,500。生产 V2 保持原本 4,500；评估版本的 V2 是 5,500，实际最高输出 2,075，未触及原上限；最终评估脚本已恢复 4,500。

新的 `conversation_progress` SQLite 表不写入 CRM Profile。状态分开记录明确要求、已证实动机、未证实假设、可让步点、异议、已沟通事实、销售尝试与客户反应、未答问题、承诺以及下一机会。完整消息仍是准绳；每轮优先据消息修正旧摘要。例：SCV3-12 把“偏好四房”列为明确要求，工作空间及偶尔母亲留宿列为已说出的原因，把三房是否足够保留为待确认，而不是直接称为硬性不合适。SCV3-05 的最终客户明确要求四间独立卧室，不能再推荐三房。

Support 与 Handoff 沿用现有系统动作。离线 `FakeOperations` 接受请求为 OPEN，只有明确的模拟事件可改为 RESOLVED；正式交接仅表示受理，`appointment_confirmed=false`。WAITING、RESUMED、END 不靠真实计时。本轮 12 个真实 API 场景未注入合成 Support 结果；RESUMED 由假传输测试验证，不可当成真人跟进能力。评估后的修正还复用了扩展措辞的相同 OPEN 请求，并把笼统“已登记”回复改为写出实际待核查事项。该修正未作第二次付费 A/B。

Customer Simulator 用 GPT-6 Luna / Medium，只看到自己的人设、私有需求、对话与可见运营状态；不看策略、版本或评分。可以继续、等待或结束。Judge 用 GPT-6 Luna / Extra High（API 接受了 `xhigh`，无模型或推理档位回退），只看匿名 A/B 客户可见对话以及分开的项目事实与授权名称规则；不看隐藏人设或内部策略。评分权重：客户洞察 25%、有意义的销售动作 25%、观察与调整 20%、自然连贯 20%、推进与节奏 10%。严重事实、库存、价格、运营承诺另列；人工销售判断不能由关键词规则代替。

## 验证与评估范围

- 本地 40 项重点测试通过；最终真实入口的假传输运行完成 12/12 对。覆盖 SQLite 进度、明确事实与假设、知识上下文、请求复用、WAITING/RESUMED/END、正式交接抑制、incomplete 用量和 V2 默认值。测试与付费模拟未调用真实 WhatsApp、CRM、客户库、预约或生产 Handoff。
- 付费 A/B 完成 12/12 对；每对共享起始情境与项目证据，后续客户行为可因回复而变化。客户对话数 V2 合计 36、V3 合计 40；有待核查事项时自然 WAITING，未强迫凑足 10 轮。完整逐轮对话、客户状态、销售动作、盲评理由在 [完整逐轮报告](aggregate.md) 和各 `SCV3-xx.pair.json`，例如 [四房硬性不合](SCV3-05.pair.json)、[需求变化](SCV3-09.pair.json)、[可让步四房偏好](SCV3-12.pair.json)。

## 运营、用量和未解决问题

最终付费记录为 **148 次完成的 API 调用**、输入 **477,926**（其中缓存 32,386）、输出 **133,650**、合计 **611,576 tokens**；所记录调用的延迟总和 **1,526.181 秒**。脚本按输入 $0.10、缓存输入 $0.01、输出 $0.50 / 百万 tokens 估算 **$0.111703**；这不是账单金额。分角色：V2 25 次 / $0.017711；V3 Strategy 29 次 / $0.017570；V3 Conversation 28 次 / $0.020457；Simulator 52 次 / $0.007890；Judge 14 次 / $0.048075。Judge 的 14 次包括首案两次因证据配置不完整而保留的旧判定；最终每对只采用一次。暂停时尚在途的请求无返回 usage，是否计费未知。完整用量与每次延迟在 `*.calls.jsonl`；本轮已返回的请求没有 incomplete。V3 Strategy 最高实际输出 2,554，V3 Conversation 最高 1,902。

Fake Adapter 记录了所有 OPEN 请求；本轮没有假装这些请求已完成。逐轮 Judge 有时把“已登记”标为没有运营支持，因为它只看客户可见对话；对照动作日志，相应请求确已在假 Adapter 受理。这些标记是 Judge 可见性限制，不应误报成系统未登记。另一方面，V3 在 SCV3-11 未限定的月费计算是真问题；SCV3-09 两个语义重叠的布局请求也是真问题，付费评估版本未拦截，评估后已补上复用测试与实现。SCV3-10 的草稿交接问题已修正模拟脚本。评估后的改动没有再付费验证，不可把本轮 2.62 分称作最终代码的实测分数。

**决策：**保持生产 V2。V3 继续是隔离实验；先在以后获得新授权时用生产等效的假传输再次覆盖完整运营路径，再考虑新的真实客户或 API 评估。不要根据这一轮继续反复调 Prompt 来制造 V3 获胜。没有部署、合并、真实发送、CRM 写入、真实预约或购买 API 额度。
